# vaulty-keeper database tunnel · usage examples

> [中文](db-proxy-examples.zh-CN.md) | English
>
> Every command below was tested against the local Docker test environment (`scripts/dbtest.sh`).
> Ports/tokens change on every run; the examples use that run's values. Per-connection tokens come from `vaulty-keeper db connect <name>`; the `TOKEN=$(cat ~/.vaulty/bridge-token)` pattern in this file still works for legacy connections (or when you want the easy route) — the tunnel also accepts the global bridge token as a fallback.
> Companion: architecture diagrams in `docs/db-proxy-architecture.md`.

## 1 · One-minute start

```sh
# ① Create the DB key (Keychain; env fallback VAULTY_KEEPER_DB_KEY)
vaulty-keeper db init

# ② Register connections (URL via stdin, never a CLI argument)
printf 'postgres://app:pgpass@127.0.0.1:59918/appdb' | vaulty-keeper db add pgdb
printf 'mysql://sha2user:sha2pass@127.0.0.1:59919/shop' | vaulty-keeper db add mysql-orders
printf 'redis://:redispass@127.0.0.1:59920/0' | vaulty-keeper db add cache

# ③ List connections (name/type/port only, never the URL)
vaulty-keeper db list
#   cache (redis) :15434
#   mysql-orders (mysql) :15441
#   pgdb (postgres) :15432

# ④ Start serve (mask bridge + all tunnels; token written to ~/.vaulty/bridge-token)
vaulty-keeper serve --addr 0.0.0.0:8972
#   serve keeps running and syncs db.json every 2 s: db add / db rm take effect immediately, no restart

# ⑤ Let vaulty-keeper print the ready-to-run client command with the token filled in, then copy-paste it
vaulty-keeper db connect pgdb
#   # pgdb (postgres) — token is this connection's dedicated tunnel token, NOT the real database password (tunnel port 15432)
#   # dedicated tokens are generated by db add and rotated with db regen <name>|--all; legacy connections fall back to the global bridge token
#   Raw tunnel link (AI / other tools can convert it as needed):
#     postgresql://5d321a50...:x@127.0.0.1:15432/appdb
#   psql / libpq (paste into psql, pgAdmin, DBeaver):
#     postgresql://5d321a50...:x@127.0.0.1:15432/appdb
#   DBeaver / DataGrip / IntelliJ (JDBC):
#     jdbc:postgresql://127.0.0.1:15432/appdb?user=5d321a50...&password=x
#   pgAdmin4 (fill fields): Host=127.0.0.1 Port=15432 Database=appdb Username=5d321a50... leave password empty
vaulty-keeper db connect cache
#   ... Redis Insight / DBeaver URL + redis-cli command
vaulty-keeper db connect pgdb --cmd        # one-line command only (for scripts)
vaulty-keeper db connect pgdb --container  # swap in host.docker.internal

# Tunnel switch: on by default; close tunnels you don't need with db off (port stops listening, serve picks it up within ~2 s)
vaulty-keeper db off pgdb
#   Tunnel for connection "pgdb" is off ('vaulty-keeper db on pgdb' to re-enable)
vaulty-keeper db list            # pgdb (postgres) :15432 [off]
vaulty-keeper db on pgdb
vaulty-keeper db off --all       # turn all off / all on (--all)
```

## 2 · Multiple same-type connections (3 MySQL, each with its own tunnel)

```sh
# Same MySQL server, 3 different databases → 3 connections, 3 ports
printf 'mysql://u:p@host:3306/shop'           | vaulty-keeper db add mysql-orders    --port 15441
printf 'mysql://u:p@host:3306/shop_billing'   | vaulty-keeper db add mysql-billing   --port 15442
printf 'mysql://u:p@host:3306/shop_reporting' | vaulty-keeper db add mysql-reporting --port 15443

vaulty-keeper db list
#   mysql-orders    (mysql) :15441
#   mysql-billing   (mysql) :15442
#   mysql-reporting (mysql) :15443

# Each connection is independent (different port, no interference)
vaulty-keeper db connect mysql-orders     # mysql ... -P 15441 ... shop
vaulty-keeper db connect mysql-billing    # mysql ... -P 15442 ... shop_billing
vaulty-keeper db connect mysql-reporting  # mysql ... -P 15443 ... shop_reporting
```

Without `--port` the port is auto-assigned (starting at 15432 and skipping conflicts); a manual port must not collide with another connection.

## 3 · Connecting with each client

First, what these clients are (the names printed by `vaulty-keeper db connect`):

| Client | What it is | Best for |
|---|---|---|
| **psql** | PostgreSQL's **bundled CLI** client (comes with a PostgreSQL install) | CLI / scripts |
| **mysql** | MySQL's **bundled CLI** client (comes with a MySQL install) | CLI / scripts |
| **redis-cli** | Redis's **bundled CLI** client (comes with a Redis install) | CLI / scripts |
| **DBeaver** | Universal database **GUI** (one app for PG/MySQL/Redis…), uses JDBC links | GUI users |
| **pgAdmin4** | PostgreSQL's **official GUI** | GUI users |
| **MySQL Workbench** | MySQL's **official GUI** | GUI users |
| **Redis Insight** | Redis's **official GUI** | GUI users |

> The CLI clients (psql/mysql/redis-cli) ship with the database itself — nothing extra to install;
> the GUI tools (DBeaver/pgAdmin4/Workbench/Insight) are separate downloads.

### psql (PG)
```sh
TOKEN=$(cat ~/.vaulty/bridge-token)
# local
psql "postgresql://$TOKEN:x@127.0.0.1:15432/appdb"
# container / AI isolation domain
psql "postgresql://$TOKEN:x@host.docker.internal:15432/appdb"
```
- token goes in the **user** field, the password field is a placeholder `x` (tunnel lets it through trust-style; the password is ignored)
- once connected, the actual session is the real account from the registered URL (e.g. `app`), on the registered database

### mysql (MySQL)
```sh
TOKEN=$(cat ~/.vaulty/bridge-token)
mysql -h 127.0.0.1 -P 15441 -u "$TOKEN" -px --ssl-mode=DISABLED shop
```
- token goes in **username**, any password works (`-px` is just any password)
- `--ssl-mode=DISABLED`: the client↔tunnel leg is plaintext; TLS between tunnel↔real DB is decided by the registered URL (`?tls=true`)

### redis-cli / Redis Insight
```sh
TOKEN=$(cat ~/.vaulty/bridge-token)
redis-cli -h 127.0.0.1 -p 15434 -a "$TOKEN" --no-auth-warning
```
- token goes in the **first AUTH command** (URL form `redis://x:$TOKEN@127.0.0.1:15434/0` also works, with a placeholder user field)

### GUI (DBeaver / pgAdmin4 / Redis Insight)
| App | How to fill it |
|---|---|
| DBeaver | JDBC URL: `jdbc:postgresql://127.0.0.1:15432/appdb?user=<TOKEN>&password=x` |
| pgAdmin4 | Host `127.0.0.1` / Port `15432` / DB `appdb` / Username `<TOKEN>` / leave password empty |
| Redis Insight | connection URL: `redis://x:<TOKEN>@127.0.0.1:15434/0` |

> Every tunnel link carries **user+password**: the token lives in PG/MySQL's user field / Redis's AUTH password,
> and the other field is a placeholder `x` (ignored by the tunnel), purely to satisfy tools/parsers that require both fields.

## 4 · Container-AI view (simulated)

```sh
# Inside a container (agent isolation domain / any container) connect to host tunnels:
TOKEN=...   # VAULTY_KEEPER_BRIDGE_TOKEN, injected by compose
psql "postgresql://$TOKEN:x@host.docker.internal:15432/appdb"
redis-cli -h host.docker.internal -p 15434 -a "$TOKEN"
# list tunnels (readable without the DB key — goes through the mask bridge)
vaulty-keeper remote dblist
vaulty-keeper db list            # falls back to the bridge automatically when there's no local store
# or grab the ready-made commands
vaulty-keeper db connect pgdb --container
```

## 5 · Read/write permissions (not enforced by the proxy — it's up to the account)

```sh
# A connection registered with a read-only account → SELECT only, writes rejected (measured)
mysql -h 127.0.0.1 -P 15441 -u "$TOKEN" -px --ssl-mode=DISABLED \
  -e "CREATE TABLE shop.demo(...);"
#   ERROR 1142 ... CREATE command denied to user 'sha2user'  ✅ rejected

# To give AI write access → register a URL with a writable account
printf 'mysql://root:rootpass@127.0.0.1:59919/shop' | vaulty-keeper db add mysql-admin --port 15444
```
Principle: **the registered account's permissions are the ceiling of what AI can do through the tunnel**. The safe posture is registering a dedicated read-only account (e.g. `app_ro`) whose name is not sensitive.

## 6 · Security checks (what AI can see / can't get)

```sh
TOKEN=$(cat ~/.vaulty/bridge-token)
# negative: any wrong token is rejected
psql "postgresql://WRONG:x@127.0.0.1:15432/appdb" -c "SELECT 1;"
#   server closed the connection

# the real account name is visible (inherent to a real session)
psql "postgresql://$TOKEN:x@127.0.0.1:15432/appdb" -c "SELECT current_user;"
#   app

# the password is not obtainable: a restricted account is denied when reading hashes
psql "postgresql://$TOKEN:x@127.0.0.1:15437/appdb" -c "SELECT rolpassword FROM pg_authid;"
#   ERROR: permission denied for table pg_authid

# audit log (success/reject only, no SQL/credentials)
grep dbproxy /tmp/vaulty-keeper-dbtest-serve.log
#   dbproxy: pgdb: 127.0.0.1:xxx: authenticated, tunnel open
#   dbproxy: pgdb: 127.0.0.1:xxx: invalid bridge token in user field
```

## 7 · Automation scripts (take these and use them)

```sh
#!/usr/bin/env bash
set -euo pipefail
TOKEN=$(cat ~/.vaulty/bridge-token)

# use db connect to generate commands, swap host/port, and run
read_orders() {
  docker run --rm mysql:8.4 mysql -h host.docker.internal \
    -P 15441 -u "$TOKEN" -px --ssl-mode=DISABLED --batch \
    -e "SELECT COUNT(*) FROM shop.orders WHERE qty >= 2;"
}
read_orders   # → 2 (orders with qty>=2)

# Redis cache write
redis-cli -h 127.0.0.1 -p 15434 -a "$TOKEN" --no-auth-warning set last_sync "$(date -u +%FT%TZ)"
```

## 8 · Checks & troubleshooting (db test / db show)

```sh
# db test: verify a registered connection can authenticate (AI-safe; prints no URL/password/address)
vaulty-keeper db test mydb
#   OK: mydb (postgres) user=app db=appdb
vaulty-keeper db test bad-db
#   FAIL: bad-db: connection failed: cannot reach PostgreSQL (check the URL's host/port)
#   fix: printf '<correct URL>' | vaulty-keeper db add bad-db (port stays the same)   ← port unchanged, DBeaver untouched

# db show: verify the registered real URL yourself (your TTY only; AI/scripts always rejected)
vaulty-keeper db show mydb
#   name: mydb
#   type: postgres
#   port: 15432
#   url:  postgres://app:pgpass@127.0.0.1:59918/appdb
```

Admin operations:

```sh
vaulty-keeper db rm mysql-billing --yes          # remove a connection (tunnel disappears too)
vaulty-keeper db shell cache                     # open an interactive client on the host (TTY-only, credentials via env)
vaulty-keeper db list --json                     # JSON output (AI-friendly)

# troubleshooting
grep dbproxy /tmp/vaulty-keeper-dbtest-serve.log # connection audit
lsof -nP -iTCP:15441 -sTCP:LISTEN            # is the port listening?
```
